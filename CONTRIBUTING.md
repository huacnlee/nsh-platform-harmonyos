# Contributing Guide

Contributions are welcome. If you find a bug or have an idea, please open an issue or submit a pull request.

This repository is a community platform for [Native Shell](https://github.com/longbridge/nsh) (NSH): the HarmonyOS /
OpenHarmony backend, built on NSH's public platform extension points. Issues and pull requests about it belong here,
not in `longbridge/nsh`. A problem that also happens on NSH's own backends (iOS, Android, desktop) is an NSH issue.

Please write clean code that follows the style and organization of the existing code, and make sure all checks pass.

Please submit **one PR that does one thing**. It makes your change easier to review and faster to merge.

Before writing code, read [docs/architecture.md](docs/architecture.md) and, for embedding, [docs/embedding.md](docs/embedding.md).

## Scope

- **Follow NSH, don't fork it.** This backend carries out what NSH's core and `nsh/base` describe, with ArkUI's
  native views. New elements, props, style keys or JS APIs are proposed to NSH first; a change here that only exists
  on HarmonyOS is accepted when it is a platform-specific capability with no shared equivalent.
- **Match the other backends' behavior.** When ArkUI differs from iOS or Android, aim for the behavior NSH documents
  and the Android backend implements, and say in the PR where it still differs.
- **Use the extension points.** If something cannot be built on NSH's public platform extension points, open an issue
  or PR in `longbridge/nsh` for the extension point instead of working around it here.

## AI-Assisted Contributions

AI-assisted contributions are welcome, including pull requests where all the code was generated by AI. What matters
is whether the change is thoughtful, focused and well validated; the contributor is responsible for the result.

Before opening a pull request, please make sure that:

- The problem is real and the change is necessary.
- The code has been reviewed by you and properly tested: unit tests where the behavior allows it, and a run on an
  emulator or device for platform code (screenshots or recordings are encouraged for UI changes).
- The pull request focuses on one thing and keeps the diff as small as practical. Ask the AI to avoid unrelated
  refactors, cleanup or formatting. **Less is better.**

### Describe public API changes

A pull request that adds, changes or removes anything public — a Rust type or function of `nsh-platform-harmonyos`,
an ArkTS API of the template, a CLI command or flag, an `nsh.json` key — lists it in the description under a
`## Public API` section, with the signature and one line on what each item is for. Changes to existing public items
go under `## Breaking Changes` with a `diff` block showing the old and the new usage.

## Commits and pull requests

Commit subjects and pull request titles name the area first, then say what changed as an imperative sentence:

```
<area>: <What the change does>
```

- The area is the part of the backend the change is about, in lower case: a module of `nsh-platform-harmonyos`
  (`text`, `scroll`, `render`, `input`, `navigation`, `media`, `accessibility`, `services`, `interop`, `app`), `cli`
  for `nsh-platform-harmonyos-cli`, `template` for the DevEco project template, or `examples`, `docs`, `ci`. Name one
  area only, never several separated by commas: when a change spans several, name the part it is mostly about.
- The sentence starts with a capital letter, uses the imperative mood, has no trailing period and fits in about 72
  characters with its area. It says what the change does for a user, not which files moved:
  `scroll: Flush the final scroll position before reporting scroll end`, not `scroll: Update mod.rs`.
- Do not use conventional prefixes (`fix:`, `feat:`, `chore:`). Pull requests are squash merged and GitHub appends
  their number: `text: Center text within explicit line heights (#1)`.
- The body (optional for small changes) explains why, wrapped at 72 columns: the problem, the approach and what it
  costs.

Examples:

```
text: Center text within explicit line heights
scroll: Flush final scroll position before reporting scroll end
render: Share one GLES 3.0 shader set across effects
cli: Sign the HAP without DevEco Studio
```

## Development and Testing

### System dependencies

- Rust through rustup, with the `aarch64-unknown-linux-ohos` target: `rustup target add aarch64-unknown-linux-ohos`.
- The OpenHarmony NDK, API 20 or later (`OHOS_NDK_HOME` set to an SDK's `openharmony` directory, the one with
  `native/`).
- DevEco Studio or HarmonyOS's command-line tools (`hvigorw`, `ohpm`, `hdc`) to build, install and run a HAP.

### Checks

Run these before opening a pull request (CI runs the same, see [.github/workflows/ci.yml](.github/workflows/ci.yml)):

```sh
cargo test --workspace
cargo fmt --all
cargo clippy --workspace --all-targets -- -D warnings
# the backend itself, with the NDK's toolchain set up as in ci.yml
cargo clippy -p nsh-platform-harmonyos --target aarch64-unknown-linux-ohos -- -D warnings
cargo clippy -p nsh-platform-harmonyos --target aarch64-unknown-linux-ohos --features dev -- -D warnings
```

`nsh-platform-harmonyos` is only compiled for real on the OHOS target, so platform code is checked by the
`--target aarch64-unknown-linux-ohos` runs; CI also checks the `api-23` and `api-26` features.

### Run on a device or emulator

```sh
cargo install --path crates/nsh-platform-harmonyos-cli
nsh run examples/counter --target harmonyos      # builds, installs and starts it on the device hdc sees
```

If you change visible behavior, run the related NSH gallery demo and attach before / after screenshots to the PR.
